# 开发过程与工作流说明

> 版式口径：Markdown正文约1–1.5页，按A4纵向、20mm页边距、14px微软雅黑、1.65行高预览；实际分页随渲染器变化，不声称所有预览均精确同页数。正文不包含代码与长附录，详细证据链接另列。

## 先立契约，再逐段实现

本项目实际用Codex辅助开发，应用运行时接入DeepSeek/deepseek-flash，两者不是同一个“开发模型”声明。题面任意Vibe Coding工具与Claude Code结合Deepseek V4 Pro存在口径差异，尚待出题方确认。没有虚构使用其他工具或已获许可。

我先让Codex核查本机条件与Skills，再把题面前三部分分为明确要求、用户决定、设计建议和待确认事项。SDD阶段建立讨论、阵容、公开发言及证据关系和API契约；DDD阶段先完成中文首页/阵容页，再接演播厅。每轮只实现授权模块，避免一个Prompt生成全部应用。SQLite迁移逐步从草稿扩展到阵容和运行，旧数据与公开事件必须保留。

TDD阶段先运行会因缺少行为而失败的测试，再最小实现并回归。依赖错误或编译错误不算业务RED。随后把真实SQLite、Express、SSE与浏览器串起来，只在模型边界使用Fake或本地HTTP替身。Provider、runner与网页的通过证据分别记录，不以替身证明真实内容质量。真实阵容和短讨论另行一次性授权，发送前持久化计数、成功或失败后关闭；阶段7没有新增官方调用。

## Skills与人的判断

Superpowers的brainstorming用于确认阶段边界与设计，writing-plans拆小任务；test-driven-development约束先失败再实现，systematic-debugging要求先找到失败位置，verification-before-completion要求实际运行再宣称通过。frontend-design用于已有页面设计；交付阶段只读取固定版本的security-best-practices和web-design-guidelines进行专项审查。Skills提供方法，不替代代码证据、用户授权或人工讨论质量判断。

## 三个真实问题与修正路径

第一，阶段5C的E2E配置在worker再次求值时创建了不同数据库，页面与断言不在同一测试环境。通过检查进程配置与SQLite记录定位，统一本轮路径、补充自有任务清理后再跑全套；没有删除失败记录或开自动重试掩盖问题。

第二，6B临时启动命令把原生Fetch的ok属性当作方法，并吞掉TypeError，最终误报未就绪且关闭授权。修复阶段先用本机响应复现，再保存共享的类型化readiness/launch，区分连接、HTTP、契约与编程错误。旧授权虽然0请求仍保持关闭；R1使用新的明确授权，不能把两次验收拼成连续成功。

第三，交付核对发现普通入口写死Fake、五组用户可见样例缺失。先测试默认安全、显式真实模式与导入幂等/事务回滚，再补最小接线。随后从候选提交导出到新目录，不复制私有配置、库或依赖，按README重装与验证，避免“只在我的工作目录能跑”。

## 对工程化AI开发的理解

工程质量依赖可追踪的契约、失败证据和复现边界。模型文本是待校验的数据，不能控制系统身份、预算和状态；公开内容与隐藏推理、诊断必须分开。引用ID存在只能证明关联合法，不能证明语义或外部事实正确。R1虽完成两次专家发言和总结，中途提炼合法为空，也不能据此宣称非空共识质量通过。保留这些限制、真实Prompt及Git演进，比一份看似完整却不可追查的演示更有价值。
