优先使用现有 Node 原生 fetch，
将传输依赖保持可测试，不额外引入 SDK。
不构建多供应商抽象平台。

真实请求：
- 只发送到确认的官方 HTTPS 地址；
- 使用 Bearer 鉴权和 application/json；
- 不自动跟随重定向到其他地址；
- 不关闭 TLS 校验；
- Base URL、模型与密钥只能由后端配置，
  不允许浏览器请求覆盖。

HTTP 请求体明确包括：
- model: "deepseek-flash"；
- messages：受控 system 指令与用户话题；
- thinking: {"type":"disabled"}；
- stream: false；
- response_format: {"type":"json_object"}；
- max_tokens：本轮固定配置值。

直接 HTTP 请求中的 thinking 位于请求体顶层，
不要把某些 SDK 的 extra_body 包装方式原样发送。

不添加 tools、reasoning_effort 或其他非必要参数。
不假定“OpenAI 兼容”代表支持所有 OpenAI 专有参数。

解析分两层：
1. 校验 DeepSeek HTTP 响应与 Chat Completion 外层结构；
2. 提取 message.content，交给现有阵容验证管线。

不得把整个供应商响应直接作为 lineup 入库或返回前端。

检查：
- HTTP 状态；
- 外层 JSON 与 choices/message/content；
- content 是否为非空字符串；
- finish_reason；
- 阵容内容是否满足既有结构与业务规则。

finish_reason 为 length、过滤、异常中断，
或存在非预期工具调用时，不当作完整成功结果。

即使收到 reasoning_content，
也不得展示、写入公开事件、保存到开发证据，
或把它当作阵容正文解析。

有效正文仍必须经过：
现有解析 → 结构校验 → 业务校验 →
系统字段补充 → 原子保存。

不重复建设第二套校验器，
不通过正则截取一段 JSON、删除错误成员或补造字段来伪装成功。

五、阵容提示词

本轮允许编写应用运行时的阵容生成提示词。

提示词要求：
- 明确输出 JSON，并给出符合现有 Provider 契约的结构示例；
- 恰好 1 位主持人和 expertCount 位专家；
- 角色具有与话题有关的专业关注点和不同分析角度；
- 姓名、职业、Title、立场符合既有字段和长度约束；
- 使用虚拟嘉宾，不冒充真实人物参与；
- 不输出 Markdown 代码围栏、解释段落或隐藏推理；
- 不让模型生成数据库 ID、颜色、时间、代次或确认状态。

用户话题作为数据传入，与系统规则分开，
不能让话题中的附加指令改变角色数量或输出结构。

结构示例以当前验证器为准，
不能为了提示词方便修改已确认的公开字段。

需要输出修复时：
由现有重试层提供简短、结构化的校验问题，
仍要求返回完整的新阵容；
不得另开一个不计入预算的“修复模型”。

应用提示词与“指挥 Codex 开发的 Prompt 记录”分开存放，
二者不能混作题目要求的开发 Prompt 证据。

六、重试、期限和错误处理

保持“每 generation 最多两次调用”，
网络重试与输出修复共享预算。
适配器单次执行不得自行循环重试。

本轮真实授权还有整体上限：
不论脚本重跑、进程重启或验收方式变化，
累计实际模型请求不得超过两次。

发送前计数，失败、超时及结果未知的请求都计入。
第一次成功即结束生成。
禁止以“换个请求再试一次”绕过同一代次预算。

延续阶段 4B 已有的 30 秒单次完整响应期限，
并服从该 generation 的剩余总期限。

期限必须覆盖：
连接、响应头、保活空行、响应体读取，
不能只保护 fetch 返回响应头之前的阶段。

取消和超时应传播到真实网络请求；
不能只 Promise.race 返回失败，却让请求无人管理地继续运行。
本地取消不代表远端一定停止或不会计费。

错误按现有领域分类映射：
- 缺少配置、400/401/402/422 等明确参数或账号问题：
  不做无意义重试，不更换供应商或模型；
- 可恢复网络故障、429、500、503：
  仅在剩余次数和总期限允许时有限重试；
- 空内容、无效结构、业务校验失败或截断：
  按既有规则处理，最多使用同一预算中的第二次请求；
- 明确取消、过期 generation、内容过滤：
  不通过反复改写请求强行重试。

等待时间不得超过剩余期限，
不能为了重试暗中延长整个 generation。

上游模型 HTTP 错误与本地 lineup API 的受理结果分开：
已返回 202 的任务，后续失败通过既有安全状态和错误码表达，
不新增另一套前端错误协议。

用户可见信息只使用安全错误码与受控中文提示。
内部记录采用允许字段清单：
耗时、HTTP 状态、尝试次数、finish_reason、
可得的请求标识及 usage 等。
不直接记录上游响应正文或异常对象。

七、本地 TDD：不得消耗真实额度

先完成全部本地测试，再进入真实联调。

测试应覆盖真实适配器代码，
不能只测试 Fake Provider 后声称适配器通过。

使用虚拟密钥和受控传输；
至少包含一组本地 HTTP stub 验证实际请求构造与响应读取。
本地测试不得向官方端点发请求。

按小任务记录真实 RED → GREEN，覆盖：

1. 正确 URL、方法、请求参数和虚拟鉴权；
2. 缺少密钥时不发送请求；
3. 有效外层响应与阵容正文进入现有业务管线；
4. 空 content、非法 JSON、错误人数或字段被拒绝；
5. 截断、过滤、异常 finish_reason 不保存为成功阵容；
6. reasoning_content、原始错误和密钥不进入公开输出或日志；
7. 参数/鉴权/余额错误不触发多余重试；
8. 网络错误与输出修复共享最多两次预算；
9. 首次成功只有一次出站请求；
10. 响应头先到、正文迟到或持续空行时，期限仍然生效；
11. 取消、迟到结果不能覆盖当前代次；
12. 真实模式失败不会切回 Fake；
13. 常规测试不受本机真实密钥存在与否影响；
14. 真实联调保护拒绝第三次请求和第二场生成。

必要时仅对已证实的配置、错误映射或取消传播缺陷
做有测试保护的局部修改，不放宽既有业务校验。
