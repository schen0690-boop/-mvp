四、先核对草稿输入与系统字段

本轮验收规则如下，若与既有契约冲突应明确报告：

1. 话题

- 必须是字符串；
- 去除首尾空白后不能为空；
- 中文、内部空格和引号应按约定保留；
- 已有长度限制则沿用；
- 未明确的长度规则单独提出建议，不冒充题目要求。

2. 专家人数

- 默认 4 位专家，不包含主持人；
- 合法范围为整数 1–8；
- 缺省与非法值分开处理；
- 不把 0、null、空字符串等都通过真假值判断变成 4；
- 字符串数字、小数、布尔值及越界值按契约拒绝；
- 本轮不实际创建主持人和专家记录。

3. 系统字段

- 标识、初始状态、创建时间等由服务端控制；
- 客户端不得通过附加字段将草稿直接设成运行中或已确认；
- 只从经过验证的输入中提取允许字段；
- 不将整个请求对象直接展开写入数据库。

未知字段是拒绝还是忽略，遵循现有契约，
但无论采用哪种方式，都不能影响受保护的系统字段。

使用真正的运行时校验。
不得用类型断言、as any 或关闭类型检查来代替校验。
不为两个输入字段无必要地增加一整套新框架。

五、实现最小业务行为

A. 创建草稿

- 合法输入创建一条独立草稿；
- 初始状态符合已确定的生命周期；
- 不启动模型调用、后台讨论任务或专家执行；
- 不预填虚构阵容、发言、共识；
- 非法输入不得留下部分业务数据；
- 同一话题允许创建不同的独立草稿，
  不擅自将话题设为唯一键；
- 两场同时运行的限制，不限制草稿数量。

创建请求的重复执行或幂等行为遵循现有契约。
若未定义，不擅自承诺“网络重试绝不会重复创建”。

B. 单条查询

- 按标识返回正确记录；
- 不存在的记录返回约定错误；
- 返回字段符合公开 API 契约；
- 不返回数据库对象、内部路径或调试信息。

C. 列表查询

- 按已有契约提供列表能力；
- 空数据库返回合法空列表；
- 记录之间不串数据；
- 排序规则明确且可测试；
- 草稿不得误标为正在进行的讨论；
- 不扩展成复杂搜索、分页平台或管理后台。

六、数据库实现要求

- 只创建本轮必要的业务表、约束及初始化能力。
- 使用参数绑定，不拼接用户输入形成 SQL。
- 数据库连接、业务服务、HTTP 监听入口适当分开，
  测试导入模块时不得自动占用正式端口。
- 初始化重复执行不删除已有数据。
- 数据库关闭后重新打开仍可读取已经提交的草稿。
- 不把正式数据库路径写死为某个测试文件。

如果既有契约要求创建草稿时同时持久化公开事件，
本轮实现这一项最小写入，并保证必要的事务一致性；
不因此展开完整事件总线或 SSE。
不得绕过已经确定的数据与事件一致性约定。

开发数据库、探针数据库、测试数据库必须分开。
测试显式使用本轮创建的独立临时数据库，
不得清空开发库或删除用户已有文件。

七、HTTP 与错误边界

沿用既有契约中的路径、状态码和错误结构。

需要处理：

- 合法创建；
- 业务输入校验失败；
- JSON 格式错误；
- 请求体形状不正确；
- 查询记录不存在；
- 受控的内部异常。

错误响应不得泄露：
SQL 原文、数据库路径、完整调用栈或敏感配置。

不得将所有错误返回成成功状态。
内部诊断日志与客户端响应分开。

JSON 可以正常作为 API 传输格式。
题目禁止的是把内部 JSON 原文直接展示到页面，
不是禁止接口使用 JSON。

本轮服务仅监听本机回环地址。
不要求配置模型密钥才能运行草稿功能。

八、按小任务执行真实 TDD

使用现有 test-driven-development Skill。

对每个关键行为执行：

1. 先写体现预期业务行为的测试；
2. 实际运行，确认因业务行为未实现而失败；
3. 写最小实现；
4. 运行同一测试并确认通过；
5. 运行有关回归测试，再整理代码。

可以先建立测试运行所需的配置和最小接口骨架，
但不能先实现全部业务，再补写测试。

依赖缺失、语法错误、路径错误不算有效业务 RED 证据。
也不能复用阶段 1B 的反向断言自检冒充本轮 TDD。

至少覆盖以下行为，按实际规则组织为独立测试：

- 正常中文话题创建与读取；
- 人数省略时使用约定默认值；
- 人数上下界合法；
- 非法人数类型、越界与小数被拒绝；
- 空白话题和非字符串话题被拒绝；
- 客户端不能覆盖系统状态等字段；
- 非法输入不落库；
- 相同话题可以形成不同标识的独立草稿；
- 可以保存超过两个草稿，不误用运行容量限制；
- 单条查询及不存在记录；
- 空列表和约定排序；
- 带引号的话题正确保存和读回；
- 数据库重开后可通过业务访问层读取；
- 初始化重复执行不破坏已有数据；
- HTTP 格式错误与内部错误的响应边界；
- 若本轮包含事件写入，其必要事务一致性。

单元测试验证校验与业务规则。
集成测试必须使用真实 SQLite 和实际业务代码。
HTTP 集成测试应经过真实 Express 请求处理流程，
不能只验证 mock 被调用了几次。

错误路径可以使用受控故障注入，
但不能将整条正常读写链路替换成假实现。

测试用例不得依赖执行顺序或共享上一项测试的数据。
退出时正确关闭本轮启动的服务和数据库。
